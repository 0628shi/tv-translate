# 安卓「无字幕剧集」实时翻译可行性分析（v2.0）

**版本** v2.0 ｜ **日期** 2026-11-02 ｜ **替代** v1.0（v1.0 面向"有字幕"的 OCR 方案）

> 需求修正：目标内容**没有字幕**。这意味着 v1.0 的主路线（屏幕 OCR）直接失效——画面里没有字可读，只能从声音里"生成"字幕。问题性质从"翻译文字"变成"实时听译"，难度上升一个量级。

---

## 0. 结论

**能做，但它是「AI 生成字幕」，不是「翻译字幕」；预期要按"能看懂剧情"设定，不是"字幕级"。**

| 场景 | 可行性 | 延迟 | 质量 | 说明 |
|---|---|---|---|---|
| 本地文件 + **先转写后看**（批处理） | ★★★★★ | 预处理 1–5 分钟，播放时 0 | 最高，接近人工字幕 | 推荐作为 MVP |
| 本地文件 + **边看边译**（流式） | ★★★★ | 句末后 1–2.5s | 中上 | 同一套内核的实时模式 |
| 流媒体 App + 音频捕获 | ★★ | 2–4s | 中 | 取决于 App 是否允许捕获 |
| 电视/外放 + 麦克风 | ★★ | 2–4s | 中下 | 兜底，环境噪声影响大 |
| DRM 平台（Netflix 等） | ★ | — | — | 音频同样拿不到，非 Root 无解 |

**四个关键数字**（真实剧集、中端机、经验估计）：

- 端到端延迟：**2–4 秒**（说话 → 译文上屏），落后约一句台词
- 英语 WER：**5–12%**；日语/韩语：**10–20%**（云端）；端侧再差 10 个点
- 单集成本：云端 **¥1–4**；端侧 **0**，但耗电和包体明显
- 开发量：批处理 MVP **2–3 周**；加实时模式 **5–8 周**

**一句话**：无字幕场景下，**"先转写、再翻译、后观看"是质量最高也最稳的形态**；实时听译是体验补充，不是主力。如果目标内容在流媒体 App 里且音频也被禁，那就只剩麦克风一条路，质量会明显打折。

## 1. 需求变化：从"识别"到"生成"

| 维度 | 有字幕（v1.0） | 无字幕（本文） |
|---|---|---|
| 输入 | 画面里现成的文字 | 音频波形 |
| 核心环节 | OCR | ASR（语音识别） |
| 输入确定性 | 高（字就在那） | 低（口音、音乐、重叠对话） |
| 时间轴 | 字幕自带 | 要自己生成 |
| 错误来源 | 识别错字 | 听错词 → 翻译放大 |
| 可校对性 | 有原文可对照 | 观众不知道原文，错了也看不出 |
| 延迟 | 0.5–2s | 2–4s |

**结论**：无字幕不是"少了一个数据源"，而是换了一个更难的问题。原来 OCR 的错误率是个位数，ASR 在剧集音频上的错误率是两位数，而且会一路传导到译文。

## 2. 四条路线

### 路线 A：本地文件 · 先转写后看（批处理）

```
视频文件 → 抽音频 → 整集 ASR（带词级时间戳）→ 断句 → LLM 翻译 → 生成 SRT/ASS → 播放器加载
```

- 优点：质量最高（可带全剧上下文、可人工校对）、播放时零延迟、实现最简单（不需要悬浮窗/录屏权限）。
- 缺点：要先等 1–5 分钟；只适用于本地文件。
- 适合：下载党、生肉党。

### 路线 B：本地文件 · 边看边译（流式）

```
播放器旁路 PCM → VAD 切句 → 流式 ASR → LLM 翻译 → 覆盖在画面上的滚动字幕
```

- 优点：即开即看，体验连贯。
- 缺点：质量低于批处理；延迟 2–4s；实现复杂度高（VAD、端点、断句、流式渲染）。
- 适合：不想等预处理、或边下边看。

### 路线 C：流媒体 App · 音频捕获

```
AudioPlaybackCapture → 流式 ASR → 翻译 → 系统悬浮字幕
```

- 优点：能覆盖第三方 App。
- 缺点：**源 App 可以拒绝捕获**（`ALLOW_CAPTURE_BY_NONE`），DRM 内容不可捕获；还要处理悬浮窗、后台保活、Android 14+ 授权。
- 现实：主流流媒体多数会关掉捕获，命中率不高。

### 路线 D：麦克风 · 电视/外放

```
麦克风 → 降噪/VAD → 流式 ASR → 翻译 → 悬浮或本机显示
```

- 优点：完全绕开 DRM 和捕获限制，任何屏幕都能用。
- 缺点：远场拾音、混响、背景音乐，WER 比线路音频高 5–15 个点；延迟更高。
- 适合：电视大屏、投屏场景。

### 路线 E：有字幕时的 OCR（v1.0 方案，降级保留）

如果片源其实带硬字幕（日文字幕、英文字幕、CC 轨），OCR 仍然比 ASR 准得多，应当优先使用。详见 v1.0 的分析，本文 §9 保留摘要。

**字幕源优先级**（工程上必须自动判断，能不用 ASR 就不用）：

```
外挂字幕文件 > 内嵌字幕轨（含 CC） > 画面硬字幕（OCR） > 音频（ASR）
```

## 3. ASR 选型

### 3.1 方案对比

| 方案 | 代表 | 语言 | 剧集质量 | 延迟 | 成本 | 离线 | 集成难度 |
|---|---|---|---|---|---|---|---|
| 云流式 ASR | 阿里/讯飞/腾讯、Deepgram、AssemblyAI | 多 | 高 | 200–500ms 出字 | ¥1–5/小时 | ❌ | 低 |
| 云批式 ASR | OpenAI Whisper、阿里录音文件识别 | 多 | 最高 | 非实时（1–3 分钟/集） | ¥1–5/小时 | ❌ | 低 |
| 端侧流式 | sherpa-onnx（zipformer/paraformer） | 中英强，日韩弱 | 中 | 100–300ms | 0 | ✅ | 中 |
| 端侧批式 | whisper.cpp（tiny/small） | 多 | 中/低 | 分块 2–5s | 0 | ✅ | 中 |
| ML Kit GenAI 语音识别 | Google（Alpha） | 中英日韩等 | 中–高 | 低 | 0 | ✅ | 低 |
| ML Kit GenAI 语音翻译 | Google（Alpha） | 有限语对 | 中–高 | 低 | 0 | ✅ | 低 |
| 自建 faster-whisper | PC/NAS/GPU | 多 | 最高 | 可近实时 | 电费 | 局域网 | 中 |

### 3.2 云端 ASR

- 流式 WebSocket，返回中间结果和最终结果，通常自带标点。
- 优点：接入快、质量好、日韩也能打；缺点：要联网、按小时计费、音频要上传。
- 国内可选：阿里云智能语音、讯飞、腾讯云；海外：Deepgram、AssemblyAI、OpenAI。
- **建议作为 MVP 的第一实现**——先把产品和体验跑通，端侧后面再补。

### 3.3 端侧 ASR

- **sherpa-onnx**：目前 Android 上最成熟的方案，AAR 直接集成，支持流式 zipformer、paraformer、whisper 等；中文/英文模型几十 MB 到 200MB，RTF 在中端机上约 0.1–0.3，实时性够。
- 日/韩端侧模型质量明显弱于云端，且选择少；这是语言相关的硬伤。
- 优点：免费、离线、隐私好；缺点：包体大（+50–200MB）、耗电、日韩效果一般。
- **建议作为第二批**，优先覆盖中/英。

### 3.4 ML Kit GenAI（2026 年的新选项，但要谨慎）

Google 在 2026 年推出了 ML Kit GenAI 的语音识别与语音翻译 API（Alpha）：

- **Speech Translation**：设备端直接做「语音 → 译文」，流式返回，官方示例包含 `ja-JP → en-US`、`en-US → es-ES`。
- **Speech Recognition**：支持从文件或麦克风流式转写，带词级时间戳；`基本`模式覆盖 Android 12+ 的多数设备，语言包含中/英/日/韩。
- 硬门槛：需要 Gemini Nano V4、**至少 4GB 可用存储**、AICore、特定旗舰芯片（Tensor G5/G6、骁龙 8 系新平台、天玑 9300/9400+ 等），且**解锁 Bootloader 的设备不支持**。
- Alpha 阶段，无 SLA、接口可能变；国内机型的 AICore/Gemini 可用性存疑。

**判断**：方向很对（端侧、低延迟、隐私），但**不能作为 MVP 的依赖**。可以作为"高端机型增强"：检测到支持就走它，否则走云端或 sherpa-onnx。

### 3.5 选型建议

| 阶段 | ASR | 理由 |
|---|---|---|
| MVP | 云流式（国内一家 + 一家备份） | 最快验证产品，质量够 |
| 增强 | sherpa-onnx（中/英） | 离线、免费、隐私 |
| 高端增强 | ML Kit GenAI | 设备支持就用，零成本 |
| 可选 | 自建 faster-whisper | 个人重度使用，质量/成本最优 |

## 4. 语言与质量预期

| 源语言 | 云 ASR WER（剧集） | 端侧 WER | 主要难点 |
|---|---|---|---|
| 英语 | 5–12% | 8–18% | 俚语、连读、背景音乐 |
| 中文 | 5–15% | 8–20% | 口音、方言、同音词 |
| 日语 | 10–20% | 20–35% | 敬语、人名、同音词多、语速快 |
| 韩语 | 10–20% | 20–35% | 连音、敬语、方言 |
| 泰语 | 15–30% | 无成熟端侧 | 声调、分词 |

> 以上为经验估计，必须用真实片段实测。剧集音频比新闻/有声书难：配乐、音效、耳语、多人抢话。

**质量衰减链**：ASR 错 10% → 翻译再错 5–10% → 观众感知到"这句话不对劲"的比例约 15–25%。所以**术语表和上下文纠错不是锦上添花，是必需品**。

## 5. 延迟预算（实时模式）

| 环节 | 耗时 | 说明 |
|---|---|---|
| 采集/重采样 | 10–30ms | 48k → 16k 单声道 |
| VAD 端点检测 | 200–500ms | 句尾静音判定 |
| 流式 ASR 出字 | 200–500ms | 中间结果 |
| 断句/标点/纠错 | 50–200ms | 可与翻译合并 |
| LLM 翻译首 token | 300–800ms | 流式输出 |
| 渲染 | 16ms | |
| **句末 → 译文上屏** | **1.0–2.5s** | |
| **说话 → 译文上屏** | **2–4s** | 落后约一句 |

优化手段：

- **中间结果先显示**：ASR 出半句就先上原文（浅色），译文到了再替换；
- **流式翻译**：不等整句，按分句出译文；
- **缓存**：重复台词、片头片尾、常见寒暄直接命中；
- **端点调优**：静音阈值 300–500ms，太短会切碎句子，太长会拖延迟。

## 6. 翻译层：ASR 纠错 + 上下文 + 术语表

无字幕场景下，翻译层的职责比有字幕时更重——它要同时干"纠错"和"翻译"。

### 6.1 联合纠错与翻译

不要"先纠错、再翻译"（两次往返、延迟翻倍）。直接给 LLM：

```
你是影视字幕翻译。下面是语音识别的原始转写，可能有同音字错误。
请结合上下文和术语表，直接输出自然的中文译文，不要解释。

术语表：金秀贤=김수현；会长=회장；...
上文：
  [前 5–10 句原文 + 译文]
本句：
  [ASR 原始转写]
```

模型会顺带修掉人名、术语、明显同音错误。

### 6.2 上下文

- 滚动窗口：最近 5–10 句（多了会贵、会慢）。
- 场景摘要：每 5–10 分钟让模型压缩一次"当前场景/人物关系"，作为系统提示。
- 术语表：角色名、地名、组织名、称谓习惯；可在第一集前 50 句自动抽取，人工可改。

### 6.3 输出约束

- 中文 ≤ 18 字/行，最多 2 行；超长自动缩句而不是硬折行。
- 保留语气词和称谓（"哥""前辈""老师"），不要过度书面化。
- 数字、单位、专有名词统一。

### 6.4 降级链

```
LLM（带上下文） → LLM（无上下文） → 通用 MT → 显示原文
```

超时 1.5s 就降级，不要让用户等。

## 7. 字幕生成、断句与同步

### 7.1 批处理管线

1. 抽音频（MediaExtractor + MediaCodec，或 ffmpeg 兜底 AC3/DTS）
2. 整集 ASR，拿到词级时间戳
3. 断句：按标点 + 停顿 + 最大时长（≤ 6s）/ 最大字数
4. 翻译：按 20–30 句一批，带上下文，JSON 对齐
5. 生成 SRT/ASS；校验行数、时间轴单调性
6. 播放器加载，双语/单语可切

### 7.2 实时滚动字幕

- 屏幕底部固定 2–3 行，最新一句在最下。
- 未定稿（ASR 中间结果）用浅灰，定稿变白，译文替换原文。
- 句末后保留 2.5s 再淡出。
- 字幕位置、字号、背景可调；不要挡住人脸（默认底部安全区）。

### 7.3 时间轴

- 批处理：词级时间戳直接生成，误差 < 200ms。
- 实时：以"句末 + 翻译完成"时刻上屏，天然滞后；不做强行对齐，否则会跳字。

## 8. 关键工程难点

| 难点 | 影响 | 对策 |
|---|---|---|
| 背景音乐/音效 | WER +5–10 个点 | 人声分离（可选，成本高）、VAD 调参、置信度过滤 |
| 多人重叠对话 | 只能识别出一条流 | 无法根治；提示"可能不准"，或只保留主声道 |
| 人名/术语 | 前后不一致 | 术语表 + LLM 纠错 + 全剧缓存 |
| 无标点 | 断句错、翻译碎 | 云端 ASR 自带标点；端侧加标点模型 |
| 口音/方言 | WER 明显上升 | 选支持方言的云服务；提示用户 |
| 耳语/气声 | 识别不出 | 增益归一化；接受漏句 |
| 片头片尾/广告 | 生成垃圾字幕 | VAD + 音乐检测 + 低置信度丢弃 |
| 长静音 | 误触发 | 端点检测 + 最短语音时长 |

## 9. 有字幕时的降级路径（v1.0 摘要）

如果片源其实有字幕（外挂/内嵌/硬字幕），优先走 OCR，不要用 ASR：

- 外挂/内嵌字幕：直接解析，质量最好、零延迟。
- 硬字幕：屏幕或画面 OCR，ML Kit bundled（中/日/韩/拉丁），延迟 0.5–1.5s。
- 屏幕捕获受 `FLAG_SECURE`/DRM 限制；悬浮窗可能被 `setHideOverlayWindows` 隐藏。

详见 v1.0 文档（本目录历史版本）。

## 10. 内容源与权限

| 内容源 | 音频能否拿到 | 结论 |
|---|---|---|
| 本地文件（自带播放器） | ✅ 直接解码 | 最稳，MVP 首选 |
| 本地文件（第三方播放器） | ⚠️ 需音频捕获或录屏内录 | 不如自己做播放器 |
| 非 DRM 流媒体 App | ⚠️ 看 App 是否允许 `AudioPlaybackCapture` | 命中率一般，需实测 |
| DRM 流媒体 | ❌ 不可捕获 | 非 Root 无解 |
| 电视/外放 | ✅ 麦克风 | 质量打折，兜底 |

**必须提前实测**：拿目标 App 播 30 秒，开 `AudioPlaybackCapture` 录一段，看是否有声、是否是静音。这是无字幕方案的第一道生死线。

- Kotlin + Compose + Media3/ExoPlayer

- 字幕：自研 SRT/ASS 生成与渲染（不自带样式，只要文本和时间轴）

## 13. 风险矩阵

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| ASR 质量不达预期（尤其日韩/带音乐） | 中高 | 致命 | Phase 0 用真实片段实测；不达标就换云服务或改做"有字幕"场景 |
| 流媒体音频被禁 | 高 | 高 | 先做本地文件；流媒体只做"支持列表" |
| 延迟 3s+，观感"慢半拍" | 中 | 中 | 中间结果先显示、流式翻译、端点调优 |
| 云端成本/隐私 | 中 | 中 | 端侧兜底、按需上传、明示隐私政策 |
| 端侧模型包体/性能 | 中 | 中 | 按需下载模型，不打包进 APK |
| 版权（生成字幕传播） | 中 | 高 | 只做个人使用，不内置分享/字幕站 |
| 系统级竞品（AI 字幕/同传） | 高 | 中 | 靠术语表、质量、跨端差异化 |

---

## 14. Phase 0 PoC（建议立刻做，2–3 天）

1. 选 3 段真实片段，各 5 分钟：英语剧（对话密集）、日剧（含人名/敬语）、韩剧（含配乐）。
2. 云端 ASR 跑一遍，人工转写对照，算 WER。
3. LLM（带上下文 + 术语表）翻译，人工评"可读率"和"术语一致性"。
4. sherpa-onnx 端侧跑同一段，对比质量/延迟/功耗。
5. 测端到端延迟：句末 → 译文上屏。
6. 测流媒体音频捕获：目标 App 能否录到声。

**Go 判据**：英语 WER < 15%、日韩 < 25%；可读率 > 85%；延迟 < 3s；目标内容源至少有一条路能拿到音频。

**No-Go / 转向**：如果日韩 WER > 30% 或音频完全拿不到，就退回"有字幕 OCR"或只做英语。

## 15. 结论与待确认

**结论**：

- 无字幕场景**可行**，但产品定位是"AI 生成字幕/听译"，不是"字幕翻译"。
- **质量最高的形态是本地文件批处理**（先转写后看），实时是体验补充。
- 英语最稳，日韩次之，泰越等更弱；语言选择直接决定成败。
- 流媒体 + DRM 仍然是墙，音频捕获不比屏幕捕获宽松。

**待确认（决定方案走向）**：

1. **主要语言**：英语 / 日语 / 韩语 / 其他？（决定 ASR 选型和预期）
2. **内容在哪**：本地下载文件 / 流媒体 App / 电视大屏？
3. **能否联网**：云 ASR 可接受吗，还是必须离线？
4. **设备**：什么机型？（决定端侧 ASR 可行性）

## 16. 最优解速查

**产品形态**：本地播放器 + 整集转写 + LLM 翻译 + 生成字幕；实时只留给直播/追更。

**三条理由**：

1. 看剧要的是"字幕和画面对齐"，不是"边说边译"。批处理在播放时零延迟，体验优于每句慢 2–4 秒的流式。
2. 质量上限由上下文决定。整集/整段可见，人名、术语、梗、指代都能处理；流式只有一句的窗口，永远追不上。
3. 工程量最小。不碰录屏、悬浮窗、音频捕获、DRM，失败模式少一半。

**流水线**：

```
导入 → 探测现成字幕（有就优先用）→ 抽音频 → 分块 ASR（5 分钟块 / 30 秒重叠）
     → 断句 → LLM 翻译（滚动上下文 + 术语表）→ SRT → 播放
```

播放不必等整集：转写进度领先播放 3–5 分钟即可开播，做到"等 1 分钟，之后零延迟"。

**选型**：云 ASR（Whisper large-v3 / 阿里 / 讯飞）+ LLM（DeepSeek/Qwen）+ Media3 + Room。

**成本**：¥1–4/集。

**不成立的条件**：内容只在 DRM 流媒体（拿不到音频）、必须完全离线（端侧日韩质量下降）、必须直播级实时。
